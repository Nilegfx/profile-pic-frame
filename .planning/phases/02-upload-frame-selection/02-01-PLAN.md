<objective>
Wire the file upload input to load user's photo onto the Konva canvas. When user selects a JPEG or PNG file, it is read client-side via FileReader, loaded as a Konva.Image node at natural pixel size, centered on the 500×500 stage, and rendered on photoLayer. The empty state placeholder is hidden after first photo load. Photo uploads are repeatable — second upload replaces the first.

**Purpose:** Enable the first user interaction — photo upload. This establishes the base layer that frames will overlay in Plan 02.

**Output:** Working photo upload flow. User can click Upload Photo → select image → see it centered on canvas → upload different image → see replacement.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User Device → Browser FileReader | User selects file from local filesystem; FileReader reads file content into browser memory |
| Browser Memory → Konva Canvas | Data URL (base64-encoded image) passed to Konva.Image.fromURL for canvas rendering |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Spoofing | File type validation | accept | File.type MIME check prevents most bypasses. accept attribute filters OS picker. Risk: low (worst case: failed image load, no security impact). |
| T-02-02 | Tampering | FileReader Data URL | accept | Data URLs generated client-side; no external input. User can only tamper own browser memory (no cross-user impact). Risk: low. |
| T-02-03 | Repudiation | Photo upload action | N/A | No logging or persistence required. Single-session tool with no accountability needs. Risk: N/A. |
| T-02-04 | Information Disclosure | Image data in memory | accept | All image data stays in user's browser memory. No network transmission, no server upload, no localStorage. Privacy-first design. Risk: none. |
| T-02-05 | Denial of Service | Large file upload | accept | FileReader can choke on very large files (>10MB) per RESEARCH.md Pitfall 6. Mitigation: accept risk for v1 (campaign photos typically <5MB). Future: add file size check if needed. |
| T-02-06 | Elevation of Privilege | FileReader API abuse | N/A | FileReader is sandboxed browser API with no privileged access. Cannot escape browser sandbox. Risk: none. |

**Summary:** All threats accepted as low risk or N/A. Client-only design eliminates most threat vectors (no auth, no server, no persistence, no multi-user concerns). Worst-case failure mode: user's browser tab hangs on huge file (10MB+). No data loss, no security breach.
</threat_model>
