<objective>
Wire the frame picker thumbnails (dynamically generated by discoverFrames() in Phase 1) to actually load frame PNG files onto the Konva canvas. When user clicks a frame thumbnail, the frame PNG is loaded via Konva.Image.fromURL, sized to fill the full 500×500 stage, and added to frameLayer (above photoLayer). The clicked thumbnail receives an active state (orange border). Clicking a different frame replaces the previous one.

**Purpose:** Enable the second user interaction — frame selection. This establishes the overlay layer that renders above the photo from Plan 01.

**Output:** Working frame selection flow. User can click frame thumbnail → see frame load on canvas → click different frame → see replacement.
</objective>

**Step 1: Create a loadFrame function**

Add a new `loadFrame(frameId, src)` function definition before the `discoverFrames()` function (around line 274). This function must implement D-03 (lazy load at selection time), D-04 (replace old frame), D-05 (size to 500×500 at x:0, y:0), and D-11 (update state):

```javascript
function loadFrame(frameId, src) {
  Konva.Image.fromURL(src, function(frameNode) {
    // D-04: Remove old frame if exists
    if (state.frameImage) {
      state.frameImage.remove();
    }

    // D-05: Frame fills 500×500 stage at top-left
    frameNode.position({ x: 0, y: 0 });
    frameNode.width(500);
    frameNode.height(500);

    // D-11: Update state
    frameLayer.add(frameNode);
    state.frameImage = frameNode;
    state.selectedFrame = frameId;

    frameLayer.draw();
  });
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local Filesystem → Browser | Frame PNG files (frame-1.png, frame-2.png, frame-3.png) loaded from same origin as index.html |
| Browser Memory → Konva Canvas | Frame image data rendered to canvas via Konva.Image.fromURL |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-07 | Spoofing | Frame file source | accept | Frame PNGs bundled with index.html — same-origin loading. No external network requests. User cannot spoof frame assets (would require filesystem access to project directory). Risk: low. |
| T-02-08 | Tampering | Frame PNG files | accept | If user tampers local frame files, only their own browser session is affected. No cross-user impact. Single-session tool with no shared state. Risk: low (self-inflicted). |
| T-02-09 | Repudiation | Frame selection action | N/A | No logging or persistence required. Single-session tool with no accountability needs. Risk: N/A. |
| T-02-10 | Information Disclosure | Frame image data | accept | Frame PNGs are campaign assets intended for public use. No sensitive data in frames. Risk: none. |
| T-02-11 | Denial of Service | Large frame PNG files | accept | Frame PNGs are bundled assets (~1.3MB each per RESEARCH.md). Known size, predictable load time. Mitigation: accept (controlled assets). |
| T-02-12 | Elevation of Privilege | Konva.Image.fromURL abuse | N/A | Konva API is sandboxed library with no privileged access. Cannot escape browser sandbox. Risk: none. |

**Summary:** All threats accepted as low risk or N/A. Same-origin frame loading eliminates most threat vectors. No user-provided URLs, no network requests, no external dependencies. Worst-case failure mode: frame PNG fails to load (shows console error, no canvas render). No data loss, no security breach.
</threat_model>
