Implementation requirements per user decisions:

- **Scale application:** Set both `scaleX` and `scaleY` to slider value (uniform scale, per D-05)
- **Centering formula (per D-04):** Recalculate offset on every slider event as `{x: naturalWidth * scale / 2, y: naturalHeight * scale / 2}` where naturalWidth = `imageNode.width()` and naturalHeight = `imageNode.height()`. Position stays at `{x: 250, y: 250}` (do NOT modify position).
- **State update:** Set `state.photoScale = scale` on each event (per D-06)
- **Redraw:** Call `photoLayer.batchDraw()` (NOT `draw()`, per D-10 for frame-rate throttling)
- **Guard:** Early return if `!state.photoImage` (no photo loaded yet)

Exact code pattern to implement (from 03-RESEARCH.md Pattern 1):
```javascript
// Wire Photo Size slider for real-time scaling (Phase 3)
const photoSlider = document.getElementById('photo-scale');

photoSlider.addEventListener('input', function(event) {
  const scale = parseFloat(event.target.value); // 0.5 to 2.0
  const imageNode = state.photoImage;
  
  // Guard: no photo loaded yet
  if (!imageNode) return;
  
  // Apply uniform scale (preserves aspect ratio per EDT-01)
  imageNode.scaleX(scale);
  imageNode.scaleY(scale);
  
  // Recalculate offset to maintain centered position (per D-04)
  const naturalWidth = imageNode.width();   // Original pixel width (no scale)
  const naturalHeight = imageNode.height(); // Original pixel height (no scale)
  
  imageNode.offset({
    x: naturalWidth * scale / 2,
    y: naturalHeight * scale / 2
  });
  
  // Update state (per D-06)
  state.photoScale = scale;
  
  // Redraw with frame-rate throttling (per D-10)
  photoLayer.batchDraw();
});
```

Insert this code block after the photo upload handler closing brace (line 402) and before the console.log statement (line 405).

**Why this approach:** Phase 2 established the centering pattern as `position(250, 250) + offset(width/2, height/2)`. When scaling, the visual center shifts because offset is in local (unscaled) coordinate space. Multiplying offset by the scale factor compensates for the scaling transform and maintains the visual center at stage coordinates (250, 250).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User slider input → JavaScript scale calculation | Slider values constrained by HTML min/max attributes (0.5-2.0), parsed as float - low risk |
| JavaScript → Konva canvas transform | Konva.js library handles transform math, no direct memory access - sandboxed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Denial of Service | Photo slider input handler high-frequency events | mitigate | Use `photoLayer.batchDraw()` (frame-rate throttled) instead of `draw()` to prevent excessive redraws - per D-10 |
| T-03-02 | Information Disclosure | Photo scale state exposed in global state object | accept | Client-side only application, no sensitive data in scale values, state object is in user's browser - no server transmission |
| T-03-03 | Tampering | User modifies slider min/max via browser DevTools | accept | Client-side tool with no persistence - user can already upload any photo and modify DOM, tampering only affects their own session |
| T-03-04 | Spoofing | N/A | accept | No authentication or identity in this phase |
| T-03-05 | Repudiation | N/A | accept | No logging or audit requirements |
| T-03-06 | Elevation of Privilege | N/A | accept | Browser sandbox contains all JavaScript execution |

**Security posture:** Phase 3 introduces no new trust boundaries beyond browser sandbox. All input is numeric (slider constrained by HTML attributes) and processed entirely client-side with no network transmission or server processing. Threat surface remains unchanged from Phase 2.
